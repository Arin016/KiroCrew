# Per-session Tool Search reload escape hatch for the /compact deferral hole (review pass v1)

Issue #8082 reports that once kiro-cli defers an MCP tool spec (context grew past `toolSearch.minPct` / `minTokens`), a later `/compact` shrinks context back below the threshold but never re-injects the deferred spec, so the tool stays invisible for the rest of the session. The root defect — deciding to defer and re-injecting after context shrinks — is in the kiro-cli deferral engine on the far side of the ACP boundary and is not fixable in this repo. This change adds `AcpProvider.reload_tool_search(*, min_pct=None, min_tokens=None)`, a manual lever that rewrites the per-session `cli.json` Tool Search overlay and restarts the kiro-cli backend so it re-reads the overlay and recomputes deferral against the current post-`/compact` context. Its shape mirrors the existing `change_effort` / `clear_effort` levers: backend-membership gating, turn-safety refusal, threshold snapshot with rollback on restart failure.

Watch for: the turn-safety guard is a check-then-act with no lock held across the restart, so a prompt that starts between the `has_active_turn()` check and `shutdown()` can still be interrupted (possible). The lever is defined but not wired to any caller (dashboard/API), so it is currently unreachable at runtime (confirmed) — intended, per the scope decision, but worth confirming it is expected for v1. One threshold-override test claims to assert write-before-restart ordering but never checks it (confirmed).

**Verdict**: APPROVED

## High-level view

The fix reuses the overlay KiroCrew already owns: it rewrites via the established `_apply_tool_search_overlay` → `_write_tool_search_overlay` path, then restarts (`shutdown()` then `start()`) so kiro-cli re-reads the overlay on a fresh spawn. This is a heavier hammer than the effort levers (which push live over a slash command or config option) because there is no in-session RPC to recompute deferral — a limitation correctly attributed upstream.

The gating matches the `change_effort` precedent: non-kiro backends, unmanaged overlay (`_tool_search is None`), disabled tool search (`False`), and active turns all return `False` without restarting. The `None`/`False` early-outs are the right call — a reload restores nothing when KiroCrew is not the one deferring.

Threshold overrides flow through the same clamped writer used everywhere else, and a snapshot/rollback protects future respawns from a poisoned override if the restart throws. The rollback is the one behavior with a mutation-tested guard.

Scoping auto-re-injection to upstream is the correct call: the deferral engine is not in this repo, cannot be unit-tested here, and a full-process restart is a strictly worse UX than the in-session recompute kiro-cli would need to implement. UPSTREAM_NOTES.md captures this and the base.py decision to keep the method off the `LLMProvider` interface until a polymorphic caller exists.

### Restart as the recompute mechanism, and the turn-safety window

Tool Search deferral has no in-session RPC equivalent to the effort levers' `/effort` / `session/set_config_option`, so the only way to force a recompute is to make kiro-cli re-read the overlay on spawn — hence `await self.shutdown()` then `await self.start()`. `start()` already re-applies both overlays before respawn, so the explicit `_apply_tool_search_overlay()` in `reload_tool_search` is redundant on the happy path; it is kept so the override is authoritative regardless of `start()`'s internal ordering, and the write is idempotent.

The turn-safety refusal (`has_active_turn()` → `False`) matches the mid-turn hazard the effort/model-switch levers document: a restart mid-turn kills the streaming prompt and can leave the native turn open with its session lock held (the class of bug the shutdown drain in `has_unfinished_turn` exists to prevent). The gap is that the check and the restart are not atomic — nothing holds a lock between the `has_active_turn()` test and `shutdown()`. If a turn begins in that window (concurrent task issuing a prompt), the restart proceeds anyway and interrupts it (possible — depends on whether the eventual caller serializes provider mutations against turn start, the way `change_effort` is invoked from a single dashboard handler). `shutdown()`'s drain mitigates the worst case (killing with an unfinished native turn), but the user-visible prompt would still be dropped. Worth confirming the intended caller holds the same serialization the effort lever relies on.

### Gating and the None/False distinction

```
backend ∉ KIRO_SLASH_COMMANDS ─→ False (claude reads no overlay)
_tool_search is None           ─→ False (overlay unmanaged, nothing to rewrite)
_tool_search is False          ─→ False (KiroCrew defers nothing, reload restores nothing)
has_active_turn()              ─→ False (never race a streaming prompt)
otherwise                      ─→ rewrite overlay, restart, True
```

`None` means the caller expressed no preference so the overlay is untouched; `False` means Tool Search is explicitly off, so no spec is being deferred by KiroCrew's overlay to restore. `_apply_tool_search_overlay()` itself already no-ops on non-kiro backends and on `None`, so these guards are belt-and-suspenders against a wasted restart, but they also produce the honest `False` return the caller needs to decide whether the lever did anything.

### Threshold override, clamping, and the missing reset

An override is applied onto `self._tool_search_min_pct` / `_min_tokens` before the overlay write, and the raw values pass through `_clamp_min_pct` (0..100, non-numeric falls back to default) and `_clamp_min_tokens` on the way to disk, so a garbage override cannot write an invalid threshold. The declared parameter type is `object`, matching the config path's own loose typing, and clamping makes that safe.

One asymmetry: a successful reload with an override leaves the mutated thresholds in place for every subsequent respawn in the session. There is no companion "reset to configured defaults" path (the way `clear_effort` complements `change_effort`). For the escape-hatch use case — operator lowers the threshold to force tools back — that persistence may be intended, but it means a one-time override silently becomes the session's standing policy. Worth an explicit decision.

### Rollback on restart failure

If `shutdown()`/`start()` raises, the thresholds are restored to the pre-call snapshot, the overlay is re-written to match, and the exception re-raises. The failure mode this guards is a half-applied override that would re-poison deferral on every future respawn; it is mutation-tested (`test_restart_failure_rolls_back_thresholds` fails when the rollback is removed, per the orchestrator's mutation check). The overlay on disk after a failed restart reflects the rolled-back thresholds, not the attempted override, which the test verifies against real `cli.json` contents.

### Test coverage

Seven async tests cover the full gating matrix (kiro happy path, claude, `None`, `False`, active turn), the override write, and the rollback, asserting against real `cli.json` via `json.loads` rather than mock call counts. The restart is observed by spying `shutdown`/`start` as `AsyncMock`.

Not tested / gaps:
- `test_threshold_override_written_before_restart` sets up an `order` list and a `start` side-effect that appends `"start"`, but never records the overlay-write event and never asserts on `order`. The comment claims "the overlay is written before start() runs" but nothing enforces it; the test only checks the final `cli.json` contents and the instance fields. Either instrument the overlay write into the same `order` list and assert `order == ["overlay", "start"]`, or remove the dead scaffolding so the test does not imply coverage it lacks.
- The turn-race window described above is not exercised (hard to unit-test without a real client); if the caller is expected to serialize, that belongs in the caller's tests.

### Reachability and the upstream scope call

`reload_tool_search` has no caller anywhere in `src/` — unlike `change_effort`, which is wired to the dashboard via `chat_handlers.py`. As written it is a correct, tested capability that nothing can currently invoke. The FEAT-002 plan explicitly deferred wiring a caller and keeping the method off the `LLMProvider` base interface until one exists, so this is a documented scope boundary rather than an oversight — but v1 should confirm that shipping the lever without an entry point is intended, since an unreachable method delivers no user-facing fix for #8082 on its own.

Leaving automatic re-injection to upstream is the right scope call. The deferral engine is not in this repo, so KiroCrew cannot make `/compact` transparently restore tools; the honest options are a manual restart (what this does) or an upstream fix (auto re-inject, or an in-session reload RPC that avoids dropping warm process state). UPSTREAM_NOTES.md records both and recommends a maintainer file the kiro-cli issue.
